# Лабораторна робота 02

Проєкт демонструє породжувальні патерни проєктування на TypeScript/NestJS.

## Запуск

```bash
npm install
npm run patterns:demo
```

Для запуску NestJS-сервера:

```bash
npm run start:dev
```

Доступні HTTP-демо:

- `GET /factory/demo`
- `GET /abstract-factory/demo`

## Пояснення патернів для захисту

Цей розділ можна використовувати як короткий конспект для відповіді викладачу без демонстрації коду. У кожному завданні показано породжувальний патерн, тобто шаблон, який відповідає за створення об'єктів і приховує деталі цього створення від основної логіки програми.

### 1. Factory Method

**Що це за патерн.** Factory Method, або фабричний метод, дозволяє базовому класу описати загальний процес створення об'єкта, але саме створення конкретного продукту передати дочірнім класам. Тобто клієнт працює не напряму з конструкторами, а з фабричним методом.

**Для чого використовується.** Патерн корисний, коли є кілька схожих продуктів, але конкретний тип продукту залежить від контексту: каналу продажу, ролі користувача, налаштувань або бізнес-правил.

**Структура в цій лабораторній.**

- Product: спільний контракт підписки. Усі типи підписок мають однаковий інтерфейс для опису своїх даних.
- Concrete Products: Domestic, Educational і Premium підписки. Це конкретні варіанти продукту.
- Creator: базовий створювач підписки. Він описує загальний сценарій покупки: перевірити тип, створити підписку, виконати додаткову обробку.
- Concrete Creators: створювачі для Website, Mobile App і Manager Call. Кожен канал сам вирішує, яку підписку можна створити і які правила застосувати.
- Client/Demo: демонстраційний сервіс викликає покупку через конкретний канал, але отримує результат через спільний контракт підписки.

**Структура папок.**

```text
src/lab_02/task1-factory/
  contracts/
    subscription.interface.ts       # Product: спільний контракт для всіх підписок
    subscription-type.enum.ts       # перелік доступних типів підписок
  subscriptions/
    domestic.subscription.ts        # Concrete Product: домашня підписка
    educational.subscription.ts     # Concrete Product: освітня підписка
    premium.subscription.ts         # Concrete Product: преміум підписка
  creators/
    subscription.creator.ts         # Creator: базовий алгоритм покупки
    website.creator.ts              # Concrete Creator: покупка через сайт
    mobileapp.creator.ts            # Concrete Creator: покупка через мобільний застосунок
    managercall.creator.ts          # Concrete Creator: покупка через дзвінок менеджеру
  demo/
    factory-demo.service.ts         # демонстрація роботи Factory Method
  factory-demo.controller.ts        # HTTP-точка для запуску демо
  task1-factory.module.ts           # NestJS-модуль завдання
```

**Як читати цю структуру.** Папка `contracts` задає абстракцію продукту, `subscriptions` містить конкретні продукти, `creators` містить фабричну логіку, а `demo` і контролер тільки запускають приклад. Головна ідея: клієнт звертається до створювача, а не створює підписку напряму.

**Як працює в проєкті.** Користувач обирає канал покупки і тип підписки. Канал не повертає об'єкт напряму випадковим способом, а проходить через спільний алгоритм базового створювача. Після цього конкретний створювач вирішує, який клас підписки треба створити. Наприклад, сайт може продавати всі типи підписок і додавати бонусний канал, менеджер також створює підписки, а мобільний застосунок блокує продаж Premium. Таким чином різні правила створення винесені в окремі фабрики.


### 2. Abstract Factory

**Що це за патерн.** Abstract Factory, або абстрактна фабрика, створює цілі сімейства пов'язаних об'єктів без прив'язки клієнта до конкретних класів. На відміну від Factory Method, тут фабрика відповідає не за один продукт, а за групу сумісних продуктів.

**Для чого використовується.** Патерн потрібен, коли система має працювати з наборами об'єктів одного стилю, бренду або платформи. Головна ідея: якщо обрано певну фабрику, усі створені продукти належать до однієї родини.

**Структура в цій лабораторній.**

- Abstract Factory: спільний контракт технологічної фабрики. Він описує, які пристрої має вміти створювати кожен бренд.
- Concrete Factories: фабрики Balaxy, IProne і Kiaomi. Кожна фабрика створює пристрої тільки свого бренду.
- Abstract Products: контракти для laptop, netbook, ebook і smartphone. Клієнт знає, що отримає пристрій певного типу, але не залежить від його конкретного бренду.
- Concrete Products: конкретні пристрої кожного бренду, наприклад Balaxy laptop або IProne smartphone.
- Registry: реєстр фабрик, який повертає потрібну фабрику за назвою бренду.
- Client/Demo: демонстраційний сервіс бере фабрику певного бренду і створює через неї повний набір пристроїв.

**Структура папок.**

```text
src/lab_02/task2-abstract-factory/
  contracts/
    tech-factory.interface.ts       # Abstract Factory: контракт фабрики бренду
    brand.enum.ts                   # перелік брендів
    " devices"/                     # фактична папка з інтерфейсами пристроїв
      ebook.interface.ts            # Abstract Product: електронна книга
      laptop.interface.ts           # Abstract Product: ноутбук
      netbook.interface.ts          # Abstract Product: нетбук
      smartphone.interface.ts       # Abstract Product: смартфон
  factories/
    balaxy.factory.ts               # Concrete Factory: створює сімейство Balaxy
    iprone.factory.ts               # Concrete Factory: створює сімейство IProne
    kiaomi.factory.ts               # Concrete Factory: створює сімейство Kiaomi
  products/
    balaxy/                         # Concrete Products бренду Balaxy
      balaxy.ebook.ts
      balaxy.laptop.ts
      balaxy.netbook.ts
      balaxy.smartphone.ts
    iphone/                         # Concrete Products бренду IProne
      iprone.ebook.ts
      iprone.laptop.ts
      iprone.netbook.ts
      iprone.smartphone.ts
    kiaomi/                         # Concrete Products бренду Kiaomi
      kiaomi.ebook.ts
      kiaomi.laptop.ts
      kiaomi.netbook.ts
      kiaomi.smartphone.ts
  registry/
    tech-factory.registry.ts        # вибирає потрібну фабрику за брендом
  demo/
    abstract-factory-demo.service.ts # демонстрація роботи Abstract Factory
  abstarct-demo.module.ts           # NestJS-модуль демо
  task2-abstarct-factory.module.ts  # NestJS-модуль завдання
```

**Як читати цю структуру.** `contracts` описує абстрактні типи фабрики і продуктів, `factories` містить фабрики конкретних брендів, `products` містить реальні пристрої, а `registry` відповідає за вибір фабрики. Головна ідея: обрана фабрика створює повний набір пристроїв одного бренду.

**Як працює в проєкті.** Спочатку обирається бренд. Реєстр повертає фабрику цього бренду. Далі клієнт викликає методи створення пристроїв: laptop, netbook, ebook і smartphone. Якщо обрана фабрика Balaxy, усі створені пристрої будуть Balaxy. Якщо замінити фабрику на IProne або Kiaomi, клієнтський сценарій не зміниться, але результатом буде інше сімейство продуктів.

### 3. Singleton

**Що це за патерн.** Singleton гарантує, що в програмі існує тільки один екземпляр певного класу, і надає глобальну точку доступу до нього.

**Для чого використовується.** Патерн застосовують для об'єктів, які мають бути єдиними в системі: конфігурація, логер, менеджер підключення, сервіс автентифікації або інший централізований ресурс.

**Структура в цій лабораторній.**

- Singleton Class: Authenticator. Це клас, для якого дозволений тільки один екземпляр.
- Private Constructor: зовнішній код не може напряму створити новий об'єкт через конструктор.
- Static Access Method: метод отримання інстанції повертає вже створений об'єкт або створює його при першому зверненні.
- Global Storage: екземпляр зберігається в глобальній області, щоб повторні звернення повертали той самий об'єкт.
- Demo: кілька разів отримує Authenticator і перевіряє, що всі посилання ведуть на один і той самий об'єкт.

**Структура папок.**

```text
src/lab_02/task3-singleton/
  authenticator.ts                  # Singleton: єдиний об'єкт автентифікації
  task3-singleton.demo.ts           # демонстрація отримання одного й того самого екземпляра
```

**Як читати цю структуру.** Тут немає багато папок, бо Singleton зазвичай концентрується в одному класі. `authenticator.ts` містить контроль створення єдиного об'єкта, а demo-файл перевіряє, що повторні звернення повертають той самий екземпляр.

**Як працює в проєкті.** При першому зверненні до Authenticator створюється один екземпляр. Він отримує свій ідентифікатор і дату створення. При наступних зверненнях новий об'єкт не створюється, а повертається той самий екземпляр. Також демонстрація показує, що зовнішнє створення через конструктор блокується.


### 4. Prototype

**Що це за патерн.** Prototype дозволяє створювати нові об'єкти шляхом копіювання вже існуючого об'єкта-прототипу. Замість того щоб збирати об'єкт з нуля, програма клонує готовий зразок.

**Для чого використовується.** Патерн корисний, коли створення об'єкта складне, має багато полів або вкладених об'єктів. Також він зручний, коли потрібно отримати незалежну копію структури і потім змінювати її без впливу на оригінал.

**Структура в цій лабораторній.**

- Prototype: клас Virus, який має метод клонування.
- Object State: властивості вірусу: вага, вік, назва, тип і список дочірніх вірусів.
- Clone Operation: клонування створює новий об'єкт з такими самими значеннями.
- Recursive Copy: дочірні віруси також клонуються, а не просто передаються за посиланням.
- Demo: створюється дерево вірусів, потім воно клонується і перевіряється незалежність копії від оригіналу.

**Структура папок.**

```text
src/lab_02/task4-prototype/
  virus.ts                          # Prototype: об'єкт, який уміє клонувати себе
  task4-prototype.demo.ts           # демонстрація глибокого клонування дерева вірусів
```

**Як читати цю структуру.** `virus.ts` відповідає за сам прототип і операцію клонування, а demo-файл створює вкладену структуру та показує різницю між оригіналом і копією. У цьому патерні ключовий файл саме той, де описаний об'єкт із методом клонування.

**Як працює в проєкті.** Спочатку створюється батьківський вірус, у якого є дочірній вірус, а в нього ще один дочірній елемент. Коли викликається клонування, створюється новий батьківський вірус і окремі копії всіх його дітей. Після цього зміна дочірнього елемента в копії не змінює дочірній елемент в оригіналі. Це означає, що реалізовано глибоке копіювання, а не поверхневе.


### 5. Builder

**Що це за патерн.** Builder відокремлює процес покрокового створення складного об'єкта від його кінцевого представлення. Один і той самий процес може створювати різні варіанти об'єкта.

**Для чого використовується.** Патерн використовують, коли об'єкт має багато параметрів, частина з них необов'язкова, або коли створення має відбуватися у певній послідовності. Builder робить створення читабельним і керованим.

**Структура в цій лабораторній.**

- Product: GameCharacter. Це кінцевий об'єкт персонажа з іменем, роллю, зовнішністю, зброєю, інвентарем і діями.
- Builder Interface: спільний контракт будівельника персонажів. Він описує кроки створення: встановити ім'я, зріст, тип тіла, колір волосся, очей, одяг, зброю, інвентар і завершити побудову.
- Concrete Builders: HeroBuilder і EnemyBuilder. Вони створюють різні варіанти персонажів: героя і ворога.
- Director: CharacterDirector. Він знає порядок кроків і збирає готового героя або ворога за заданим сценарієм.
- Client/Demo: створює директора, передає йому потрібний будівельник і отримує готового персонажа.

**Структура папок.**

```text
src/lab_02/task5-builder/
  models/
    game-character.ts               # Product: готовий персонаж гри
  builders/
    character-builder.interface.ts  # Builder: спільний контракт кроків побудови
    hero.builder.ts                 # Concrete Builder: створює героя
    enemy.builder.ts                # Concrete Builder: створює ворога
  director/
    character-director.ts           # Director: задає порядок побудови персонажа
  task5-builder.demo.ts             # демонстрація створення героя і ворога
```

**Як читати цю структуру.** `models` містить кінцевий об'єкт, `builders` містить покрокові будівельники, `director` визначає готові сценарії збирання, а demo-файл тільки запускає приклад. Головна ідея: персонаж створюється не одним конструктором, а послідовністю зрозумілих кроків.

**Як працює в проєкті.** Директор не створює персонажа одним великим конструктором. Він послідовно викликає кроки будівельника: задає ім'я, фізичні характеристики, одяг, зброю, інвентар і дії. Якщо передати HeroBuilder, результатом буде герой з добрими вчинками. Якщо передати EnemyBuilder, результатом буде ворог зі злими вчинками. Кінцевий об'єкт має однакову структуру, але наповнення залежить від конкретного будівельника.



## Коротке порівняння

| Патерн | Головна ідея | Що створює у лабораторній |
| --- | --- | --- |
| Factory Method | Делегує створення одного продукту конкретним створювачам. | Підписку через різні канали продажу. |
| Abstract Factory | Створює сімейство пов'язаних продуктів. | Набір пристроїв одного бренду. |
| Singleton | Гарантує один екземпляр класу. | Єдиний Authenticator. |
| Prototype | Створює новий об'єкт копіюванням існуючого. | Копію дерева вірусів. |
| Builder | Покроково збирає складний об'єкт. | Персонажа гри: героя або ворога. |

## Як коротко пояснити різницю

- Factory Method відповідає на питання: "Який конкретний продукт створити в цьому каналі?"
- Abstract Factory відповідає на питання: "Яке сімейство сумісних продуктів створити?"
- Singleton відповідає на питання: "Як зробити так, щоб об'єкт був тільки один?"
- Prototype відповідає на питання: "Як створити копію вже готового об'єкта?"
- Builder відповідає на питання: "Як зібрати складний об'єкт по кроках?"
